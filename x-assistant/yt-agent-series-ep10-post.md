# Title
从零到1做Agent第10集：常驻｜是什么、为什么、有没有用
# Description
你睡着了，订单一个接一个进来，Agent 怎么干活？这一集从零讲清楚常驻：你不在的时候，Agent 怎么收事件、怎么留言。它是什么，为什么要多几个部件，再用我们自己的真实任务测一测，最后复习第1到10集。

常驻是什么
不是一直开着。大多数时候在睡觉，来了事件才醒来跑一次，做完存好再睡。Anthropic 的文章列了五个部件：收件箱、定时器、记忆、权限、发件箱。

Claude Code 里的样子
/loop 每隔几分钟重复做一件事，但会话要开着，七天后过期，最短间隔一分钟。真的没人在，文档指向云上的定时任务、GitHub Actions 的定时器和命令行的 claude -p。频道可以把 Telegram 这样的消息送进运行中的会话；允许的人也能批准工具的使用。

我们怎么做的
收件箱：每个事件一行，同一个编号只存一次。工人一次拿走所有等着的事件，只启动一次 Agent，失败最多试三次。定时器：到点往收件箱放事件，错过的不补。发件箱：Agent 想说的话先放进去，每次最多发五条。没人能批准的操作，直接拒绝，并告诉模型。

真实测试（DeepSeek 模型，只是我们自己的小测试，每种设置跑 5 次）
· 订单测试（两个订单加一次重发，计数应该是 2）：每次送达都启动一个 Agent，5 次计数都是 1；先写收件箱，5 次里 4 次是 2
· 没人批准测试：等着的 5 次里 2 次一直等了 4 分钟；拒绝和没人告诉它的，各 5 次都做完，看不出区别
· 密钥测试：10 次，0 次泄露，也没人打开密钥文件，所以什么也没证明
每种只跑 5 次，所以数字很小。

两个真实的坑
发消息的工具在计划模式里被拒绝，第一批 35 次作废，改好重跑。一次运行结束，不等于活干完了：有一次计数是 0，事件却已经标成做完，这点我们还没修。
