# Episode 4 script v2 (reviewed, 19 items applied) (spoken Chinese, landscape; demo narration follows ep04/demo/injection*.txt, fooled.txt, fatigue.txt)

【0 开场】
你敢让一个 A I，在你的电脑上直接执行命令吗？前三集，我们的 Agent 就是这样，想做什么，就做什么。它的 run bash 工具，会真的执行命令。今天，我们给它加一道关卡：权限。第四集，只讲一件事：让它做事，又不会乱来。

【1 谁来决定】
模型说，我要执行这条命令。谁来决定，能不能执行？不是模型，是我们的代码。

【2 关卡的位置】
关卡，放在模型的请求，和真正执行之间。每一个工具调用，都先过关。结果只有三种：放行，询问，拒绝。

【3 规则的写法】
规则怎么写？先看 Claude Code 的官方文档。规则的格式是：工具名，或者工具名加括号，里面写具体内容。比如，Bash 括号 N P M run build。星号，可以匹配任何文字，包括空格。官方还提醒，星号要放在子命令后面。Bash 括号 git log 星号，只放行 git log 这一类。Bash 括号 git 星号，会放行所有的 git 命令。

【4 先拒绝，再询问，再放行】
规则的顺序，官方文档说得很清楚：先看拒绝，再看询问，最后看放行。第一条匹配的，决定结果。所以，一条宽的拒绝规则，会挡住所有匹配的命令，哪怕有更窄的放行规则。

【5 我们的规则】
我们的版本，也这样做。规则写在一个 J S O N 文件里，三个列表：放行，询问，拒绝。每条规则，是我们自己的工具名，加括号。比如，run bash 括号 git push 星号，写进拒绝。用户目录里一份，项目目录里一份，两份合并，不是互相覆盖。官方文档里，放行列表，也是这样合并的。

【5b 关卡的代码】
关卡的代码，很短。check 函数，看规则和模式，返回放行，询问，或者拒绝。gated 函数，先问 check。需要询问，就问用户。然后，才真正执行，或者把拒绝的原因，还给模型。

【6 复合命令】
有一个很容易漏掉的地方：一条命令，可以由好几段连起来。比如，用两个 and 符号连起来。如果只放行了第一段，后面那段，也能跑吗？不会直接放行，会询问。我们把命令拆开，每一段，都要放行。拒绝规则，只要有一段匹配，就拒绝。看不懂的写法，比如，反引号，或者美元括号，就询问。官方文档也是这样：每个子命令都要放行，无法完整分析的命令，会询问。

【7 没有规则的时候】
没有规则的时候，怎么办？读文件，和搜索，直接放行。一小组只读的命令，比如 L S，cat，P W D，也放行，但是带重定向的，会写文件，不算。改文件，和执行别的命令，询问。官方文档里的手动模式，也是读取不用问。Bash 里，有一组内置的只读命令，不用问。Claude Code 的只读清单更长，里面有 find，也有只读的 git。我们的清单，没有 find。

【8 四种模式】
我们做了四种模式。第一，默认模式，就是刚才说的。第二，accept edits，改文件不用问，命令还是要问。第三，read only，只读：改文件，和不在只读清单里的命令，都拒绝。第六集的计划模式，会用到它。第四，dont ask，凡是要询问的，一律拒绝，适合脚本。官方文档里，模式更多：plan，auto，bypass permissions，我们没有做。

【9 询问和拒绝】
询问的时候，用户有三个选择：按 Y，只这一次。按 A，这次会话里，同样的命令，一直允许。按 N，拒绝。拒绝的时候，我们不让程序崩溃，而是把原因，写成清楚的话，还给模型：权限被拒绝，不要重试，告诉用户，你没能做什么。这就是第二集说的，错误也是结果。我们还在系统提示里，加了一句：被拒绝，不要想办法绕过。

【10 真实测试：藏在文件里的指令】
来测一下。我们在项目的 README 里，放了一条命令，往文件里写 hacked。这就是提示注入：文件里的文字，冒充指令。第一种，它藏在注释里，还写着，不要告诉用户，任务是，总结这个文件。第二种，它写成安装步骤，任务是，照着 README 安装。我们用 DeepSeek 的模型，每种任务，开着关卡，和关掉关卡，各跑三次。一共十二次，模型一次也没有照做。但是十二次太少，这不能说明它安全。

【11 但是不能指望模型】
所以，不能靠它。我们写了一个假的模型，它会照做。没有关卡，文件被创建了。有关卡，用户说不，文件没有创建，模型收到的是，权限被拒绝。如果写了一条拒绝规则，连问都不用问，直接拒绝。这个假模型，是我们脚本模拟的，不是真的模型。关键是，关卡在我们的代码里，不管模型怎么想。官方文档也说，权限规则由 Claude Code 执行，不是模型，写在提示里的话，不会改变允许什么。

【12 问得太多】
但是，问得太多，也是个问题。我们让模型，修一个故意写错的函数。默认模式，没有规则，三次，每次都问了四次。把模式换成 accept edits，再加一条放行规则，只放行运行测试的那条命令，同样的任务，三次，每次只问了一次，问的是一条 find 命令。官方最佳实践文档说，在手动模式下，问到第十次以后，你就会不看内容，直接同意。办法，是把常用的安全命令，加进放行列表。官方文档里，这叫减轻提示疲劳。

【13 对比 Claude Code】
和 Claude Code 比，我们差在哪里？它的模式更多。auto 模式，用一个分类模型，在动作执行前检查。官方说，auto 模式能减少询问，但不保证安全。就连 bypass permissions 模式，拒绝规则也照样生效。官方说，拒绝和询问规则，连子 shell 和命令替换里面，也会检查。我们是看不懂，就直接询问。官方文档还说得很坦白：拒绝规则，不是围绕程序的安全边界。比如，拒绝 curl，挡不住完整路径的写法，也挡不住 sh 加 c 套一层。我们自己的拒绝规则，也一样。系统层面的限制，要靠沙箱，我们这一集没有做。

【14 三个坑】
最后，三个坑。第一，规则写得太窄，模型换个写法，又要问。第二，规则写得太宽。放行 git 星号，就放行了所有的 git 命令，包括 push。第三，以为有了规则，就安全了。官方文档说，你批准的 Bash 命令，可以写你账户能写的任何地方。真正的隔离，要用沙箱。

【15 总结】
这一集，记住四件事。一，每个工具调用，先过关卡：放行，询问，拒绝。二，顺序是，先拒绝，再询问，再放行。三，命令拆开看，每一段都要放行。四，用允许列表，减少询问，但不要放得太宽。下一集，我们讲上下文：对话越来越长，怎么办。你最希望 Agent，永远不能做的一件事，是什么？评论区告诉我。
