## MCP in Claude Code
- "an open source standard for AI-tool integrations". Four ways to add a server: HTTP ("the recommended option" for remote servers), SSE (deprecated, "Use HTTP servers instead"), local stdio ("run as local processes on your machine"), WebSocket (no OAuth).
- Commands: `claude mcp add --transport http <name> <url>`; stdio: `claude mcp add <name> -- <command> [args]`; `claude mcp add-json`, `list`, `get`, `remove`, `/mcp` in a session.
- Scopes: local (default, only this project, not shared, `~/.claude.json`), project (shared by version control, `.mcp.json` in the project root), user (all projects, `~/.claude.json`). Precedence local, project, user, plugin, claude.ai connectors; the whole winning entry is used, fields are not merged.
- Project approval: "Claude Code prompts for approval in interactive sessions before using project-scoped servers from `.mcp.json` files." In `claude -p` runs the prompt cannot be shown, so project servers load without asking.
- Tool names `mcp__<server>__<tool>`. Tool search is on by default: "Tool search keeps MCP context usage low by deferring tool definitions until Claude needs them." Only tool names and server instructions load at the start. No fixed per-server tool cap: "the practical limit is your context window budget". `ENABLE_TOOL_SEARCH`: unset/true (all deferred), auto (load upfront while under 10% of context), false.
- Safety: "Verify you trust each server before connecting it"; servers "that fetch external content can expose you to prompt injection risk". A tool can set `anthropic/requiresUserInteraction` so it always asks, even in bypass modes. Use a read-only database user in the Postgres example.
- Output: a warning above 10,000 tokens; default limit 25,000 (`MAX_MCP_OUTPUT_TOKENS`); big results are saved to a file and Claude gets the path; text over 50,000 characters is saved to a file when no limit is declared.
- The page shows no full tools/list or tools/call exchange (only fragments of tool entries).

## Skills in Claude Code
- "Create a `SKILL.md` file with instructions, and Claude adds it to its toolkit. Claude uses skills when relevant, or you can invoke one directly with `/skill-name`." "a skill's body loads only when it's used."
- Layout: `my-skill/SKILL.md` (required) plus optional reference files and `scripts/` ("executed, not loaded"). Places: personal `~/.claude/skills/`, project `.claude/skills/`, plugin, enterprise, nested folders. Follows the open Agent Skills standard.
- Frontmatter: "All fields are optional. Only `description` is recommended"; `name` defaults to the folder name; without a description Claude uses the first non-empty line. Many other fields (allowed-tools, disable-model-invocation, context, hooks, paths, ...).
- Loading: "skill descriptions are loaded into context so Claude knows what's available, but full skill content only loads when invoked." Description plus `when_to_use` are cut at 1,536 characters in the listing; the listing budget is 1% of the context window; when it overflows the least used skills lose their descriptions first; "The listing always contains every skill name."
- After a skill is invoked, its text stays in the conversation. On compaction the most recent call of each skill is re-attached, "keeping the first 5,000 tokens of each", 25,000 tokens in total.
- Advice: "Keep `SKILL.md` under 500 lines"; "Put the key use case first" in the description; keep the body short ("State what to do rather than narrating how or why"); put the most important instructions near the top.
- Safety: a skill's `allowed-tools` can grant itself tool access ("A skill can grant itself broad tool access, so review the `allowed-tools` of skills checked into a repository"); `` !`command` `` injection runs shell commands when the skill loads; `disableSkillShellExecution` turns it off.

## MCP specification (stdio, lifecycle, tools)
- Two spec versions matter. 2025-11-25: the client sends `initialize` (protocolVersion, capabilities, clientInfo); the server answers (protocolVersion, capabilities, serverInfo); the client sends `notifications/initialized`. 2026-07-28 ("latest"): "There is no negotiation handshake"; each request carries protocol version and capabilities in `_meta`; a client may call `server/discover`; legacy servers still use `initialize`. Our client: [decision for the outline].
- stdio: the client launches the server as a subprocess; messages are JSON-RPC, one per line, "MUST NOT contain embedded newlines"; "The server MUST NOT write anything to its stdout that is not a valid MCP message"; logs may go to stderr; shutdown = close stdin, wait, SIGTERM, SIGKILL.
- tools/list: result.tools (name, title, description, inputSchema as a JSON Schema object, optional outputSchema and annotations), optional cursor and nextCursor. Names 1 to 128 characters of A-Z a-z 0-9 _ - . . Annotations "MUST" be treated as untrusted unless the server is trusted.
- tools/call: params name and arguments; result content (e.g. {"type":"text","text":...}) and isError. A protocol error is a JSON-RPC error (e.g. -32602 unknown tool); a tool execution error is a normal result with isError true, "actionable feedback that language models can use to self-correct"; clients SHOULD pass execution errors to the model.
- Safety: "Tools represent arbitrary code execution and must be treated with appropriate caution." "there SHOULD always be a human in the loop with the ability to deny tool invocations." Clients should show inputs before calling and validate results before passing them to the model. Tool names are unique only within one server: prefix them when aggregating servers.
