EP12 测试和调试 Agent · 讲稿（共 36 段，卡片编号 = 段号，估计约 600 秒，真实声音大约短 8%）

【开场】
1. 你改了提示词里的一句话，跑一次，好了，就上线了。可那是这句话的功劳，还是运气？今天讲：怎么知道一次改动，到底有没有用。
2. 三个问题。怎么测？测的时候要留下什么？失败了，看哪里？数字都是 DeepSeek 一个模型跑的，四个任务，每种做法五次，很小。我会说清楚，能说什么，不能说什么。

【问题】
3. 先说问题。只跑一次，你不知道它是对，还是碰巧对。同一个任务，同样的设置，模型每次的路都不一样。
4. 这是我们真跑出来的。同一个任务，同一种做法，五次里，四次顺利做完。有一次，回答了两次就停了。第一条命令被拒绝，它就放弃了。只看那一次，你会以为这个改动坏了。

【是什么】
5. 先把词说清楚。任务，是一道固定的题，有输入，也有判对的规则。试验，是把这道题做一次。模型每次不一样，所以每道题，要做好几次。
6. 评分器，是一小段代码，负责打分。我们看结果，不看话。比如改版本号，就把程序运行起来，看它打印的是不是新版本。它嘴上说改好了，不算数。
7. 轨迹，是一次试验完整的记录：每条消息，每次工具调用。分数告诉你对不对，轨迹告诉你为什么。
8. 每道题做五次，可以算两个数。五次里对几次。还有，五次是不是全对。上线的东西，要看后一个。再认两个量。轮，是模型回答一次。token，是模型读文字的小块，像把一句话切成碎片。读了多少 token，是每一轮读到的内容，加起来的总数。

【文章和 Claude Code】
9. Anthropic 工程博客，二零二六年一月九日，有一篇文章，讲怎么评测 Agent。它建议：从真实的失败里，找二十到五十个简单的任务，就是很好的开始。能用代码判的，就用代码判。再靠人读轨迹。
10. 文章还说了两件事。一个任务，如果很多次都是零分，多半是题或者评分器坏了，不是模型笨。另一个，如果一个测试已经接近百分之百，它只能防退步，已经看不出进步了。
11. Claude Code 里，没有现成的测试框架，给你自己的任务用。但有几样东西可以搭。claude 加 p，是不开界面、一次跑完。输出格式选 json，会给你结果、会话编号，和一个估算的费用。选 stream json，每个事件一行。
12. 还有两个上限。最多多少轮，和最多花多少钱。钱是估算，不是账单。再有，调试用的开关，可以按类别过滤，也可以写进文件。出了怪事，用安全模式，把你的各种定制全关掉。要是问题没了，就是被关掉的东西惹的祸。还有一个叫 restricted 的开关，文档写明，是给评测用的。
13. 会话记录，Claude Code 存成文件。可文档明说，这个格式是内部的，版本之间会变。所以别靠它做测试。你要自己存。

【我们自己做的】
14. 我们自己做的，叫 eval。四道固定的题，每道题每种做法，各跑五次。
15. 第一件事，每次试验，都从一份干净的项目拷贝开始。上一次改过的文件，不能留到下一次。我们有一项检查，专门测这个。
16. 第二件事，评分器看结果。改版本号，就运行程序，看它打印什么。改税率，就算一遍。加折扣函数，用没给过它的例子，再算一遍。
17. 第三件事，每次试验，整串消息，存成一个文件。最后出一张表：对几次，平均几轮，读了多少 token。
18. 一次只改一处。两种做法，只差规则里的一句话，别的全一样。这一集的代码，有二十项检查，不用 A P I key，就能跑。

【真实测试】
19. 四道题，都在同一个小商店项目里。改版本号。把税率从百分之七改成百分之八。加一个折扣函数，还要写测试。最后一题，只读：问订单一零四二的状态，而且不许改任何文件。
20. 评分一道题，有好几项。比如税率五项：配置改了，说明文件改了，测试没有报错，测试里的期望值改了，程序算出来对。全对才算过。
21. 改动，我们在跑之前，就写下来了。这一句：改一个值的时候，搜索整个项目，把别的地方也一起改。我们的猜测是：版本号和税率，这种散在几个文件里的值，会更容易全改对，多花几轮。
22. 两个量，前面说过。轮，是模型回答一次。读了多少 token，是每一轮读到的内容，加起来的总数。
23. 看一次真实的试验。税率，不加那句话。它先搜索，读了五个文件，改了配置，说明，和两处测试，最后再搜一遍。一共六轮。五项全过。

【结果】
24. 看结果。不加那句话，四道题，二十次，全对。加了，十八次对。版本号，五次里四次。折扣，五次里四次。税率和只读，都是五次全对。
25. token。版本号，平均从一万三千九百，到一万八千。税率，从一万三千八百，到一万九千二百。多了三成到四成。只读，几乎一样。折扣，加了那句话平均是两万二，可是里面有一次提前停了，只有一千七百。另外四次，平均两万七千六，比不加多了大约四分之一。可是每次差得很大，版本号加了那句话，最少一万二，最多两万三。所以，多花是个线索，不是证明。二十比十八，五次一组，也分不出是那句话的影响，还是运气。
26. 有没有帮上忙？没有。不加那句话，已经全对了。这四道题，太容易了，看不出进步。这就是文章里说的，测试饱和。
27. 再读两次失败的轨迹。第一次，版本号。它去找所有的一点零点零，连更新日志里，第一版的那一条，也并进新的一条里。历史被改没了。这是那句话可能带来的坏处。可是只有五次里的一次，证据很弱。
28. 第二次，折扣。第一条命令，是一条查找加显示的长命令，权限规则不让。它照规则，没有绕开，就停了。看起来跟那句话没关系，是权限设置。不加的五次没碰到，样本太小，不能肯定。

【真实的坑】
29. 一个真实的坑。试跑的时候，版本号这题，我们的评分器，判它错了。为什么？它要求文件里，有一模一样的字，商店版本一点一点零。可是 Agent 做得更好：让横幅，去读配置里的版本号，不再写死。结果对，我们的评分器看不懂。
30. 这正是文章讲的：评分器太死，会把对的判成错的。我们改成运行程序，看它打印什么，再测一遍。这个改动是在正式跑之前做的，两种做法用同一个评分器。要是没人去读那条轨迹，这个错的分数，就当真了。
31. 小一点的：评分器出的结果，要写明是哪一项没过。读失败，是先看这一行，再决定要不要打开轨迹。

【总复习与结尾】
32. 总复习。第一集，循环。第二集，工具。第三集，提示词和笔记。第四集，权限。第五集，上下文。第六集，计划和清单。
33. 第七集，子 Agent。第八集，hook。第九集，记忆。第十集，常驻。第十一集，M C P 和 skill。第十二集，测试和调试。
34. 我们没有做的有这些。用另一个模型来打分。几十道题的大题库。每次改动，自动跑一遍。还有，难一点的题，让改动有空间显出差别。
35. 记住一句话：别靠一次运行下结论，先读轨迹，再信分数。下一集，把所有的部分，合成一个完整的命令行 Agent。
