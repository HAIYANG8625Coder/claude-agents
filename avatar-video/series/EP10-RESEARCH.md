## The article: an always-on agent is a loop run, save, sleep
- "Not really always on": it sleeps and wakes for a run: event arrives, session starts, agent loop runs, the run writes back to stored state. Same core loop as other agents; the difference is the architecture around it.
- Five primitives (exact list): event inbox, timers, memory, permissions, outbox.
- Inbox: triggers = webhooks, scheduled tasks, background jobs. If each source calls the agent directly: two events at once start competing runs, a crash loses an event. Simplest inbox = a durable list of events (a database table) + a handler that writes to it (acknowledge fast) + a worker that reads from it. Track event status, dedupe on source-provided unique ids, one inbox per user at first. "The inbox should be the source of truth": a dead worker's event can be picked up and retried. One active worker per inbox; a new event during a run can wait for the next run, fold into the current run, or interrupt and restart. Batch pending events so several messages get one reply.
- Timers: follow-ups (a deadline the agent sets) and schedules (recurring). Own durable store, separate from the inbox. A timer does not start a run: a scheduler polls the store, finds due timers, updates them (done, or next due time), puts an event in the inbox and wakes the worker.
- Memory: store only what the agent cannot look up again (point to other systems). Four kinds: user instructions (loaded every run), user notes (index + on-demand files), past messages (so nothing repeats), task progress (one file per task). "Dreaming" = a separate process that curates old memory (we did not build it in ep 9). Context overhead is paid every run: keep it lean, use prompt caching; compaction or a new session loses detail, so save what must persist.
- Permissions: the area of greatest risk, because a run "holds the user's access" and nobody watches. Per tool call: proceed, block, or wait for approval. Pieces: credentials kept in a proxy outside the agent's environment that adds them to outgoing requests (the agent never holds them); auto mode (classifiers review risky actions; user review still needed for the most important decisions); deferred tool calls (a hook defers a call, the run ends with the session saved mid-call, the request is shown to the user, the answer returns as an inbox event that starts a new run which resumes the session).
- Outbox: a run ends in one of three ways: a message to the outbox, nothing to send, or a deferred tool call. A simple "send" tool is enough unless you need pacing or error recovery; then a separate outbox table + dispatcher. "Better for the agent to start quiet and then earn more of the user's attention" (build evals for the volume).
- Numbers on the page: only a cost comparison (Opus 5.5 78% less per solved task than Opus 5 on a long-horizon coding benchmark, vs 40% less on typical workloads); I will not use it.

## Claude Code docs: what it has for "nobody is there"
- /loop and cron (scheduled-tasks): session-scoped, needs the machine on and the session open; `/loop 5m check the deploy`; min 1 minute; tools CronCreate/CronList/CronDelete; max 50 tasks per session; recurring tasks expire after 7 days; fires only between turns; no catch-up for missed runs (fires once when idle); disable with CLAUDE_CODE_DISABLE_CRON=1. For unattended work the page points to cloud scheduled tasks, GitHub Actions `schedule`, or Desktop scheduled tasks.
- Cloud scheduled tasks (routines, research preview): run on Anthropic's cloud, triggers = schedule, API, GitHub events; schedules more often than hourly are rejected; a run that hits an ask rule waits for someone to answer [part of this page is summary].
- Headless (`claude -p`): non-interactive; exit code 0 on success; `--output-format text|json|stream-json`; `--bare` skips hooks, skills, MCP, auto memory and CLAUDE.md (recommended for scripts, needs ANTHROPIC_API_KEY); in manual mode a call that needs approval "is denied" unless a PermissionRequest hook or `--permission-prompt-tool` approves; `--permission-prompts none` for when nobody can answer: anything that would prompt is denied, Claude is told nobody can approve and not to retry, the run continues; `--max-turns`, `--max-budget-usd`; a `-p` run without `--bare` still runs project hooks.
- Channels (research preview): "A channel is an MCP server that pushes events into your running Claude Code session"; events arrive only while the session is open, so always-on = a background process or persistent terminal; Telegram, Discord, iMessage; sender allowlist; "Anyone who can reply through the channel can approve or deny tool use in your session, so only allowlist senders you trust with that authority."
- Permission modes: default (manual), acceptEdits, plan, auto, dontAsk ("anything that would prompt is denied", for locked-down CI and scripts), bypassPermissions (only in isolated containers; no protection against prompt injection). "Auto mode reduces permission prompts but does not guarantee safety." Rules are evaluated deny, then ask, then allow; Bash argument patterns are "fragile".
- GitHub Actions: `anthropics/claude-code-action@v1`, a `schedule` cron example, `--max-turns`, secrets in repository secrets ("Never commit API keys or OAuth tokens"); scheduled runs only from the default branch.
